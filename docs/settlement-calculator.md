# Расчёт взаиморасчётов

`SettlementCalculator.Calculate(trip)` строит итоговые переводы по всем расходам поездки.
Он ничего не изменяет в `Trip` и при повторном вызове возвращает тот же результат.

Баланс каждого участника рассчитывается по формуле:

```text
balance = оплаченные расходы - доли в расходах
```

Положительный баланс означает, что участник должен получить деньги. Отрицательный —
что он должен заплатить. Сумма всех балансов обязана быть равна нулю.

Расходы и доли ограничены `792281625142643375935439503.35`, чтобы любая сумма
в этом диапазоне точно представлялась с двумя знаками и сохранялась в БД.
Для вычисленных балансов и переводов этот лимит не применяется: допустимо любое
значение, которое `decimal` может представить **точно**, без округления копеек.
Например, сумма двух максимальных расходов `1584563250285286751870879006.70`
представима как `1584563250285286751870879006.7` и успешно рассчитывается.

Денежная арифметика backend выполняется **только в `decimal`**. `BigInteger`
запрещён, переходить к нему не будем. Это обязательное решение проекта, а не
временная оптимизация. Правило закреплено также в `AGENTS.md`.

Перед сложением встречные расходы взаимно сокращаются в `decimal`: это исключает
переполнение временного общего кредита при корректном конечном балансе.
Промежуточные суммы и остатки хранят целую часть и копейки в двух полях `decimal`.
Это позволяет обнаружить потерю точности, которую обычное сложение decimal могло
бы скрыть округлением. Все операции ограничены возможностями decimal; произвольной
целочисленной арифметики нет. При формировании результата проверяется точное
совпадение целой и дробной частей. Переполнение или невозможность точного
представления даёт `OverflowException` и HTTP 422, без округления копеек.

В браузере применяется `decimal.js` с точностью 60 значащих цифр, а не `BigInt`
или JavaScript `Number`. Точности достаточно для денежных значений backend и сумм
массивов frontend. JSON содержит строки. Demo использует те же ограничения
представимости результата в .NET decimal и тот же порядок участников по ID.

После расчёта балансов участники разделяются на кредиторов и должников. Для текущей
пары рассчитывается сумма:

```text
amount = min(остаток долга, остаток кредита)
```

Для пары создаётся один перевод, затем погашенная сторона заменяется следующей.
Участники обрабатываются по возрастанию `Participant.Id`
с использованием порядка `Guid` в .NET. Поэтому результат стабилен независимо
от порядка добавления участников и загрузки коллекций из БД. Каждый перевод содержит
`FromParticipantId`, `ToParticipantId` и `Amount`; имена участников может добавить
Application или API при формировании ответа.

Пример балансов:

```text
Ivan   +40
Oleg   -10
Masha  -30
```

Результат:

```text
Oleg  -> Ivan  10
Masha -> Ivan  30
```

Жадный алгоритм создаёт не более `creditors + debtors - 1` переводов. Он хорошо
упрощает взаиморасчёты, но не
гарантирует абсолютный математический минимум количества переводов для каждой возможной
комбинации балансов: поиск такого минимума требует отдельного, существенно более
сложного алгоритма.
