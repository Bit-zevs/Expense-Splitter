# Деление расходов поровну

## Ответственность слоёв

`Trip` — группа поездки, `Participant` — её участник, `Expense` — оплаченный расход.
Плательщик (`PaidByParticipantId`) и люди, между которыми распределяется расход,
могут различаться. `ExpenseShare` хранит обязанность участника по конкретному расходу;
это ещё не перевод денег плательщику. Баланс участника можно впоследствии считать как
сумму оплаченного им минус сумму его долей.

В Domain реализованы методы `Trip.AddEqualExpense` и `Trip.AddEqualExpenseForAll`,
а сам расчёт вынесен во внутренний `EqualSplitCalculator`. `Trip` выступает корнем
агрегата: он проверяет принадлежность плательщика и выбранных участников группе,
вычисляет доли и добавляет готовый расход в `Trip.Expenses`. Необязательный
`occurredAt` задаёт время операции вручную; оно хранится в UTC с точностью до минуты.
Если значение не передано, Domain использует текущее время. Свойства сущностей
закрыты для внешнего изменения, чтобы нельзя было обойти эти правила.

Application-сценарий реализован в `CreateEqualExpenseHandler`: он сначала проверяет
поля команды, затем асинхронно загружает поездку с участниками, вызывает
`Trip.AddEqualExpense` и сохраняет результат с передачей `CancellationToken`.
Endpoint `POST /trips/{tripId}/expenses` принимает сумму, описание, ID плательщика
список выбранных ID и необязательный `occurredAt`. Он возвращает 201 с рабочим `Location` на созданный расход,
400 для некорректного запроса и 404 для отсутствующей поездки.
Infrastructure сохраняет расход и его доли в PostgreSQL: таблицы `Expenses` и
`ExpenseParticipants`, owned-коллекция `ExpenseShare` с первичным ключом
`(ExpenseId, ParticipantId)`. Оба денежных столбца имеют точность `numeric(29,2)`
и ограничения диапазона, согласованные с Domain. Конфигурации EF, начальная миграция
и интеграционные тесты находятся в Infrastructure и Infrastructure.Tests.
Подробности загрузки агрегата и ограничений БД — в [persistence.md](persistence.md).

## Все или выбранные участники

Один механизм принимает явный непустой набор ID. Пустой список — ошибка,
а не сокращение для «все». Для деления среди всех передаётся текущий состав группы.

```csharp
var selectedExpense = trip.AddEqualExpense(
    100m,
    "Ужин",
    payerId,
    new[] { aliceId, bobId, charlieId },
    new DateTimeOffset(2026, 9, 8, 19, 30, 0, TimeSpan.FromHours(5)));

var everyoneExpense = trip.AddEqualExpenseForAll(100m, "Такси", payerId);
```

Выбор и рассчитанные доли фиксируются в момент создания расхода. Добавление
участника в группу или изменение исходного списка не меняет старый расход.
`ParticipantIds` вычисляется из `Shares`, поэтому две версии состава не расходятся.
Дубликаты, пустые ID, посторонние участники и плательщик вне группы отклоняются.

## Остаток и точность

Текущая модель предполагает одну валюту с двумя десятичными знаками.
Положительная сумма должна точно выражаться в копейках; лишние знаки не округляются молча.
Максимальная сумма — `792281625142643375935439503.35`. Это наибольшее значение,
которое можно представить как целое количество копеек в `decimal`. Полный диапазон
`decimal` намеренно не поддерживается: возле `decimal.MaxValue` тип не способен
различать соседние копейки.

1. Перевести сумму в целое количество копеек.
2. Сначала вычислить остаток от деления на количество участников.
3. Вычесть остаток и разделить полученное кратное значение без округления.
4. Первым участникам в порядке `Guid` добавить по копейке, пока остаток не исчерпан.

Примеры: 100 / 3 → 33.34 + 33.33 + 33.33; 0.02 / 3 → 0.01 + 0.01 + 0.
Сумма долей точно равна расходу, различие между долями не больше копейки.
Порядок ID обеспечивает повторяемость независимо от порядка выбора в интерфейсе.
Округление каждой доли независимо может потерять или добавить деньги, поэтому не используется.

Компромисс: при повторяющихся расходах дополнительную копейку получают одни и те же ID.
Возможные следующие правила:

- Ротация получателей остатка между расходами; потребуется хранить очередь или смещение.
- Распределение с учётом ранее полученных дополнительных копеек; потребуется история и правило при равенстве.
- Явный выбор получателя остатка пользователем; это отдельное правило, способное увеличить различие долей.

Для MVP достаточно стабильного порядка. При смене правила старые доли сохраняются,
а новое правило применяется только к новым расходам или явному пересчёту.

## Другие способы деления

Для процентов, весов и точных сумм сохраняется общий результат `ExpenseShare`.
Когда появится второй способ, можно добавить отдельную фабрику и калькулятор,
расширить `SplitType` и проверять общие инварианты: уникальные ID, неотрицательные
доли, принадлежность группе и точное равенство суммы долей сумме расхода.
Интерфейс стратегий пока не нужен. Для нескольких валют следует ввести валюту
и точность её минимальной единицы, а также запретить сложение разных валют без конвертации.
